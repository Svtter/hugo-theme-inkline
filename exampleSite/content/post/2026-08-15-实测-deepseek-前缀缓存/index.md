做 agent 应用的人都关心 context cache：多轮会话每次都要把全部历史发一遍，如果命中缓存，前缀部分按缓存价计费、延迟也显著下降。但有一个很实际的问题——**同一个 session，前缀（历史消息）完全相同，只在末尾追加了一条不同的新消息，缓存还能命中吗？**

官方文档说缓存按"最长公共前缀"匹配，听起来应该能命中，但口说无凭，直接用 4 个对照请求实测一下。

<!--more-->

## 判断依据

DeepSeek 官方接口的 `usage` 里会返回两个字段：

- `prompt_cache_hit_tokens`：命中缓存的 token 数
- `prompt_cache_miss_tokens`：未命中、需要现场计算的 token 数

判断标准很简单：第二个请求的 `cache_hit` 如果接近前缀的 token 数，就是命中了。

## 实验设计

构造一个约 2900 tokens 的公共前缀：system 消息里塞了一份 59 条的《售后手册》，再加两轮确认对话，保证远超缓存的最小匹配块（64 tokens）。然后发 4 个请求：

| 请求 | 内容 | 预期 |
|---|---|---|
| A | prefix + suffixA（冷启动） | hit ≈ 0，顺便把前缀写入缓存 |
| B | prefix + suffixA（与 A 完全相同） | hit ≈ 全部 prompt tokens |
| C | prefix + **suffixB**（相同前缀，**不同后缀**） | **核心问题：hit ≈ 前缀 tokens？** |
| D | **开头改写的 prefix** + suffixB | 负对照：hit ≈ 0 |

A 发完等 15 秒——缓存是服务端异步生成的，立刻发第二个请求可能还没建好。B、C、D 连着发。D 只改了 system 消息的第一句话，后面 2900 多 tokens 的手册原文原封不动。

## 结果

| 请求 | prompt_tokens | cache_hit | cache_miss | 耗时 |
|---|---:|---:|---:|---:|
| A | 2910 | 0 | 2910 | 4.14s |
| B | 2910 | 2816 | 94 | 3.37s |
| C | 2906 | **2816** | 90 | 2.76s |
| D | 2905 | 0 | 2905 | 3.86s |

三个关键观察：

**1. C 的命中数和 B 一字不差。** 换了 suffix 之后 hit 依然是 2816 tokens，和完全重复请求的 B 完全相同；miss 的 90 tokens 正好是新 suffix 的长度。结论成立：**缓存严格按公共前缀对齐，前缀之后的尾部内容根本不参与匹配，后缀不同不影响命中。**

**2. D 的命中归零。** 只改了 system 第一句话，99% 的内容原样不动，hit 还是 0。这说明匹配是逐 token 的前缀对齐，不是内容相似度——前面断了一个字，后面全部作废。

**3. B 揭示了一个细节。** 完全重复的请求也有尾部 94 tokens 未命中（2816 恰好是 44 × 64），印证了缓存按 64-token 块对齐：提示词末尾不满一块、贴近结尾的部分不会进缓存。

延迟上，命中 97% 前缀时从 4.14s 降到 2.76s，快了约三分之一，同时命中部分按缓存价计费，省钱和加速是同步发生的。

## 使用场景

聊到一半突然冒出一个不相关的新点子，是 agent 工作流里很常见的打断。直接在当前会话里问，这段跑题内容会永久混进历史，之后的每一轮都带着它，既多花 token 又容易带偏主线；另开一个新会话，则要把背景从头再讲一遍，前面聊的内容全浪费了。

前缀缓存给出了第三种选择：**保留当前会话的完整历史，把新点子作为尾部唯一的新消息追加发出**。实验 C 恰好就是这种形态——前缀一字不改地命中，只有新点子本身按全价计费。点子聊通了就留在这个分支会话里继续，聊不通就切回原会话，两边上下文互不污染；来回切换的成本，只是一次命中缓存的请求。

## 工程启示

- **历史消息只追加、不改写。** 每轮把原样的历史带上、末尾追加新消息，就能持续命中；任何对历史的改写、重排、摘要替换，都会从断点开始作废后面的全部缓存。
- **稳定的内容放前面，多变的内容放后面。** system prompt、文档、工具定义这些每轮不变的东西放头部；最新的用户消息、动态注入的上下文放尾部。
- **前缀最好"块对齐"地稳定。** 64 tokens 一块，尾部不满一块的部分永远 miss。
- **两次请求要同一个 key、同一个模型名**，缓存不跨账号、跨模型共享。采样参数（temperature 之类）不影响匹配。
- **冷启动后留几秒余量。** 缓存异步生成，写完立刻读大概率 miss。

## 复现

实验脚本在这里：[gist: test_prefix_cache.py](https://gist.github.com/Svtter/3e18cab79027c6bcb828d2c10f99e034)


API key 只从环境变量读取，脚本里不出现明文。如果换模型后 usage 里没有 `prompt_cache_hit_tokens` 字段，脚本会把原始 usage 打出来方便排查字段名。
